# 雛形へのフィードバック

ahc_thin_harness の雛形作成担当に渡す、問題によらない指摘の一覧。問題固有のことは書かない。新しい指摘は末尾に足す。

## 1. 毎回読み込まれる指示ファイルに雛形作成の経緯を書かない（ユーザー指摘）

- 起きたこと：`AGENTS.md` に、エージェントの行動に関係しない記述が多く入っていた。
  - 「本バージョンにAB-MCTS/Beads/ダッシュボード/自動LLMモデル選択はない。わざと薄く保つ」のような作成経緯
  - 想定する大会区分や、限界の説明
  - CLIが既に強制しているルール
  - `cp config.example.json` から始まる実行例の全文

  AGENTS.md は毎回読み込まれるので、こうした記述はそのままトークンの無駄になる。`docs/SETUP.md` も、オーケストレーターに `docs/DESIGN.md` を読ませる手順になっている。
- 次の雛形で：AGENTS.md には、エージェントの行動を変える指示だけを書く。worker の `task.md` など、毎回読まれる他の指示も同じ。各行について「これが無いとエージェントの行動が変わるか」を確かめ、変わらない行は削るか、人間向けの文書に移す。オーケストレーターが読む文書は AGENTS.md だけで足りるようにする。
- このリポジトリでは：AGENTS.md を行動指示だけに書き直した（6.2KB → 3.5KB）。

## 2. `.gitignore` の `config.json` が `examples/toy/config.json` まで除外する（展開時に判明）

- 起きたこと：パターンがルートに限定されていないので、デモ用の設定がコミットされない。そのため clone した先で `demo` とテストが失敗する。
- 次の雛形で：`/config.json` とルートに限定する。
- このリポジトリでは：`examples/toy/config.json` を強制追加し、`config.json` 自体もGit管理にした。

## 3. `problem/tools/README.md` のプレースホルダが公式ツールのREADMEとぶつかる（展開時に判明）

- 起きたこと：AHCの公式ツールにはたいてい `README.md` が含まれる。そのため配置するとプレースホルダ（アダプタの約束事）が上書きされる。
- 次の雛形で：アダプタの約束事は `docs/SETUP.md` に書き、`problem/tools/` には何も置かない。
- このリポジトリでは：公式のREADMEを残し、アダプタの説明は `problem/tools/LOCAL_JUDGE.md` に書いた。

## 4. 公式ツールのビルド済みバイナリの置き場所が決まっていない（展開時に判明）

- 起きたこと：ラウンドのスナップショットと worker へのコピーでは `target/` が除外される。そのため `cargo build` の成果物をアダプタからそのまま使えず、置き場所とビルド手順を問題ごとに考えることになる。
- 次の雛形で：`problem/tools/bin/`（Git管理外）と、公式ツールをビルドしてそこへ置くスクリプトを雛形に含める。
- このリポジトリでは：`scripts/build_tools.sh` を追加した。

## 5. `claude` engine の既定値では worker が検証できず、隔離も効かない（展開時に判明、実機では未確認）

- 起きたこと：
  - `claude -p --permission-mode acceptEdits` だけでは Bash が許可されないので、worker がコンパイルや `quickcheck.py` を実行できない。
  - workspace を `git init` する隔離は Codex には効くが、`claude` は親ディレクトリの `CLAUDE.md` を読んでしまう。
- 次の雛形で：`--safe-mode`、`--permission-prompts none`、`--allowedTools`（quickcheck とコンパイラ）を付けた例を、実機で確かめてから載せる。
- このリポジトリでは：`config.json` に上記を設定した（まだ実行していない）。

## 6. 評価で現bestと候補の条件が揃っていない（展開時に判明）

- 起きたこと：
  - 現bestは単独で採点し、候補は並列で採点する。そのため時間いっぱい探索する解法では、CPUの取り合いの分だけ候補が不利になる。
  - 候補内のケースは逐次実行なので、1.8秒のソルバーだと1候補あたり約30分かかる。
- 次の雛形で：ケース単位で並列化し、現bestと候補を同じ並列度で混ぜて採点する。
- このリポジトリでは：R0003から対応した。現bestと全候補のケースを1つの待ち行列に交互に入れて並列12で採点し、各 `scores.csv` にはseed順の連続した分だけを書く（再開と早期打ち切りはそのまま）。Aの評価は約1時間から約27分、Bは約1時間から約5分になった。

## 7. Pythonの必要バージョンが実態と合っていない（展開時に判明）

- 起きたこと：READMEは3.11以上を求めるが、3.11固有の機能は使っておらず、3.10でも全テストが通る。要件に合わせて `.venv` を作ったので、コマンドが `python3` から `.venv/bin/python` に変わった。
- 次の雛形で：要件を実態に合わせるか、CLIの起動時にバージョンを確かめる。
- このリポジトリでは：`.venv`（3.12）を使っている。

## 8. `claude -p` の worker に何が渡るかは、実機で確かめないと分からない（開始前の確認で判明）

- 起きたこと：オーケストレーター（VS Code拡張）のセッションには `AGENTS.md` が読み込まれていた。worker の workspace はリポジトリの中にあるので、worker にも渡るおそれがあった。そこで config.json と同じフラグで `claude -p`（CLI 2.1.260）を起動し、読み込まれた指示を答えさせた。
  - デバッグログ（`--debug-file`）には指示ファイルの読み込みが記録されない。そのため判定はモデルの自己申告に頼り、陽性対照（自動メモリの索引 `MEMORY.md` を検出できること）で裏付けた。
  - 読み込まれた指示：

    | 起動場所 | `--safe-mode` なし | `--safe-mode` あり |
    |---|---|---|
    | リポジトリ直下 | 自動メモリの索引 | なし |
    | `git init` していないサブディレクトリ | 自動メモリの索引 | 未確認 |
    | `git init` したサブディレクトリ（worker と同じ形） | なし | なし |

  - `claude -p` は、リポジトリ直下から起動しても `AGENTS.md` を読まなかった。
  - 漏れる経路は自動メモリだった。オーケストレーターはメモリに研究の知見を書くことがあるので、索引が worker に渡ると情報漏れになる。
  - engine の argv に `--model` が無いので、worker のモデルはユーザー設定（`"model": "opus"`）で決まり、`claude-opus-5` で動いた。オーケストレーターは `claude-opus-5-5` だった。
  - `--model claude-opus-5-5` を付けると、worker は起動直後に API の400エラーで失敗した。PATH 上の `claude`（端末のCLI、2.1.260、自動更新オフ）がこのモデルに対応していなかった（2.1.280以上が必要）。オーケストレーターを動かす VS Code 拡張には、別に新しいCLI（2.1.326）が同梱されていた。
  - 2.1.326 でも、worker と同じ形では何も読み込まれなかった。リポジトリ直下から `--safe-mode` なしで起動しても、`AGENTS.md` は読まれなかった。
- 次の雛形で：
  - workspace ごとの `git init` と `--safe-mode` を両方残す。どちらか一方でも自動メモリは渡らなかったが、片方が外れても漏れないようにする。
  - engine の argv に `--model` を明示し、worker のモデルを個人の設定に左右させない。
  - worker が使うCLIのバージョンを、起動前に確かめる手順を入れる（`claude --version`、または短い `claude -p` を1回）。worker の失敗は `job.json` の `worker_failed` と `agent.stdout` でしか分からないので、10並列のAで初めて気づくと影響が大きい。
  - 上の確認手順（陽性対照つき）を、engine を初めて使うときやCLIを替えたときの手順として docs に載せる。
- このリポジトリでは：worker と同じ形では何も読み込まれないことを確かめた。`--model claude-opus-5-5` を付け、`run-workers` は VS Code 拡張に同梱のCLIを PATH の先頭に置いて実行している。

## 9. 利用上限で途中終了した worker が、完走した worker と同じ「提出済み」になる（R0002で判明）

- 起きたこと：サブスクで A（10並列）を始めて約5分で、10体中7体が5時間の利用上限に達して止まった（`agent.stdout` は "You've hit your 5-hour limit" の1行、終了コード1）。直前に B（1体32分）とオーケストレーター自身の作業があった。
  - 止まった worker も、`main.cpp` が途中まで書かれていれば `submitted` として凍結される。違いは `job.json` の `agent_outcome: error` だけで、`run-workers` の結果でも目立たない。
  - `_worker` は `submitted` の job を再実行せず、`submit`・`fail` は `prepared` の間しか使えない。`close` は未評価の提出があると拒否する。そのため、途中の版を評価するか、state ファイルを手で書き換えるしかない。
  - 完走した worker は約5分で終わっていた。A の20分は、多くの案で上限として余っている。
- 次の雛形で：
  - `run-workers` の結果で、途中終了（`agent_outcome` が `ok` 以外）を目立たせる。オーケストレーターがその job を再実行するか失敗扱いにできるコマンドを用意する。
  - 上限のメッセージを検出したら、まだ起動していない worker を起動しない。
  - 利用上限のあるプランでは、A の並列数・時間・モデル・effort を上限から逆算して決める手順を docs に書く。
- このリポジトリでは：R0002 は途中終了の7体も含めてそのまま評価した。

## 10. worker の effort が個人の設定に左右される（R0002のあとにユーザー指摘）

- 起きたこと：engine の argv に `--effort` が無かった。そのため worker の effort は、ユーザー設定（ここでは `~/.claude/settings.json` の `modelSettings` に、`claude-opus-5-5` の `effortLevel: xhigh`）に左右されうる。`--safe-mode` のもとでこの設定が効くかは確かめていない。effort が高いと、worker 1体あたりの消費が増え、9の利用上限に早く達する。
- 次の雛形で：`--model` と同じく `--effort` も engine の argv に明示する。worker の消費は「並列数×時間×effort」で決まるので、利用上限のあるプランで A と B の effort をどう選ぶかを docs に書く。
- このリポジトリでは：R0003 から `--effort high` を明示した。
