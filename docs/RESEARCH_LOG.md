# 研究の記録（オーケストレーター用）

オーケストレーターがラウンドごとに新しいセッションで始めるための引き継ぎ。worker の課題には、ここの得点や経緯を書かない。

- 各ラウンドの全文は `runs/R####/plan.json`（案）と `result.json`（効果）にある。ここには要点だけ書く。
- 効果（effect）は、そのラウンドのseedでの当時のbestとの対の差の平均。ラウンドが違う効果どうしは、目安としてしか比べられない。
- 更新の仕方：close の前に「ラウンド記録」に1節を足し、「次の狙い」を書き直す。昇格したら「現bestの系譜」に1行足す。

- 時間を伸ばしたときの伸びの大半は、骨格と予選から来た（良い初期解の差が最後まで残る）。大きく伸ばすなら、今の局所解から出られる構造の変更が要る。表し方・解き方を変える案は、親の探索に小さく足す形では効かなかった（R0015）。本気で方式を変えるなら、時間の大半を新しい方式に回す版を B で作り込む。ただし R0003 では、新しい構築法を単独で使うと −10〜−43 だった。
- 2026-11-20 の公式提出は47719、1位は47740（1ケースあたり +0.21）。提出1回のぶれ（合計±10）を考えると、1位を確実に上回るには +0.4 程度欲しい。小さな正の変更（E02 の時間配分 +0.07、R0015/A02、R0015/A09、R0016 の鎖の重み5倍 +0.10±0.09、R0014 の Optuna 最良 +0.05）を1つの B にまとめれば、+0.2〜0.3 の見込み。足し合わせて +0.15 以上になれば、1000ケースの評価でも見える。
- 最良既知解との差 +2.0 は、今の系統の計算量30倍に当たる（64秒で +1.49）。E01 では、最良解に固有の構造は見つからなかった。局所的な直し方では取れない。
- 方式を変える前に、伸びしろを確かめる価値が R0016 でさらに上がった。最良既知解と単純な上限の差（平均16点、M20〜30 で26点）のうち、どれだけが本当に縮められるかで、続ける方向が変わる。壁による遮りとPの推移を数えた下限を作るか、小さな盤面や区間で厳密解を求めて、最良既知解と比べる。

## 運用の注意

- Codex の利用上限は `python3 scripts/codex_limits.py` で読む（読み取りだけ）。評価の時間は、Aが約27分、Bが約5分（README）。
- codex の worker は WSL の DNS 失敗で時間切れになることがある（`docs/TEMPLATE_FEEDBACK.md` の13）。止まった worker は、その時点のコードで提出扱いになる。
- codex の10体の A ラウンドで、5時間枠を約42〜45ポイント使う（R0012・R0013）。
- R0015 の codex 10体の A ラウンドでは、5時間枠を61%、週間枠を9ポイント（41%→50%）使った。R0012・R0013（42〜45%）より多い。課題が重く、worker が9〜18分かかった。
- R0014 から、B の worker は調整用 seed（1000000〜1019999、同時12ケース）で `batchcheck.py` を使った多数ケースの評価と Optuna での調整ができる（`workers.tuning_B`）。engine の `codex_deep` は codex の effort を xhigh にしたもの。R0014 では、8時間の上限に対して49分で終わった（task.md の「時間を使い切る必要はない」による）。5時間枠を14ポイント、週間枠を2ポイント使った。
- R0016 から、`batchcheck.py` に、1ケースの制限時間を変える `--time-limit`（最大600秒）と、各ケースの入力・出力・標準エラー出力を残す `--keep DIR` がある。長い時間の測定に使う。R0016 の codex_deep の B（測定だけ、計算機時間の大半は待ち）は90分で終わり、5時間枠を11ポイント（61%→72%）、週間枠を2ポイント使った。
- 採点中に環境が不調になると、TLE として記録される。R0013 ではファイルシステムの破損で、baseline と A01 が同じseed・同じ時間で TLE になり、scores.csv の末尾がヌル文字になった。ユーザーの了承を得て `evaluation` を `evaluation.broken` に移し、最初から採点し直した。baseline の TLE は、まず環境を疑う。
