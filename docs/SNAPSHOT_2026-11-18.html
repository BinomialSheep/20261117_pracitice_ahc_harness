1. ハーネスの全体像

オーケストレーター1体が全履歴を見て方針を決め、実装は履歴を知らない worker に任せる。worker の成果は、オーケストレーターが新しい1000 seedで現bestと並べて採点し、良ければ明示的に best へ昇格させる。これを1ラウンドとして繰り返す。

役実体見えるものすること
オーケストレーター VS Code 上の Claude Code（AGENTS.md が指示書） リポジトリ全体、全ラウンドの結果 A/Bの選択、案の作成、CLI の実行、採否の判断、ユーザーへの報告

2. 1ラウンドの流れ

  1. 状況確認と A/B の選択

    status で途中のラウンドが無いかを見る。案には課題だけを書き、過去の得点・他候補の結果・研究の経緯は書かない。

    Aprepare A --ideas proposals.json
    10案の JSON（形式は templates/ideas.example.json）
    Bprepare B --idea '...'
    親は常に現best

  2. prepare：ラウンドの固定

    runs/R####/ を作り、plan.json に設定・seed範囲・直前のbest・案を固定する。公式ツールと問題文を judge_tools/ にコピーしてハッシュを取る。案ごとに workspace を作り、git init する。前のラウンドが close されていないと拒否する。

  3. run-workers：実装

    engine の argv で worker を起動し、task.md を標準入力で渡す。時間切れのときはプロセスグループごと止める。終了時に workspace の main.cpp を candidate.cpp として凍結し、SHA-256 を記録する。手作業なら --engine manual と submit／fail／workers-done を使う。

  4. evaluate：採点

    候補と現best を同じ1000 seedで採点し、result.json に効果（effect、正ほど良い）を書く。中断しても再実行すれば続きから採点する。

  5. promote と close

    現bestより良い候補だけを promote する。前のbestは best/history/ に残る。改善が無ければ据え置き、close で閉じる。

ラウンドの状態は state.json の phase で管理する。round コマンドは prepare から evaluate までをまとめて行い、promote と close は行わない。

prepared→ workers_done→ evaluated→ closed

job ごとの状態は pending → running → submitted → scored。main.cpp が無ければ worker_failed、評価で無効なら scoring_failed になる。

4. 評価と採用

同じ条件で比べる

  • seed：ラウンド r は seed 1000r〜1000r+999。候補と現bestは必ず同じ seed 集合で比べる。ラウンドごとに seed が違うので、別ラウンドの平均点どうしは比べない。
  • 負荷：現bestと全候補のケースを1つの待ち行列に seed 順・候補順に交互に入れ、並列12で採点する。現bestも候補と同じ負荷で走る。
  • スナップショット：judge は runs/R####/judge_tools の固定コピーを使う。worker が自分のツールを書き換えても採点に影響しない。

候補ごとの手順

  1. ソースのハッシュ・judge コマンド・seed 範囲を source.json に記録する（再開時に食い違えば止まる）。
  2. コンパイルする。失敗なら compile_error。
  3. オーケストレーター側で seed0 を採点する。worker の自己申告だけには頼らない。
  4. 1000ケースを採点し、scores.csv に seed 順で追記する。無効が出たらその候補の採点を打ち切る（early_stop_on_invalid）。
  5. 同じソース（SHA-256 が一致）は1回だけ採点し、結果を共有する。

比較と採否

effect  = mean_seed( 候補の得点 − 現bestの得点 )      # paired_difference, maximize
SE      = stdev / sqrt(n)、95%CI = effect ± 1.96 SE      # 探索的な目安
better_cases / worse_cases = 差が正／負の seed 数
  • 全1000ケースが有効な候補だけが採用できる。無効（TLE・RE・MLE・WA）は0点扱いではなく、候補ごと除外する。
  • promote は effect > promotion_margin（0.0）を満たし、ラウンド開始後に best が変わっていないときだけ通る。
  • A の1位は10本からの選抜なので、効果は過大に出やすい。新しいラウンドでは新しい seed で再び比べることになるので、ここで偏りの一部は洗い直される。

5. 問題との接続

config.json の judge.command が1ケースのアダプタ problem/tools/score_case.py を呼ぶ。

  1. 公式 bin/gen で seed の入力を作る。
  2. ソルバーを1回実行し、壁時計で2.0秒を超えたら TLE。RSS 1024 MiB 超は MLE。
  3. 公式 bin/vis で検証・採点する。
  4. 結果を JSON で書く。有効なら {"status":"ok","valid":true,"score":…}、無効なら {"valid":false,"reason":"TLE: …"}。

ツールが無いなど環境側の失敗では JSON を書かずに非0で終わる。こうしてソルバーの無効と judge の故障を区別する。

コンパイルg++ -std=gnu++23 -O2 -DONLINE_JUDGE -DATCODER（-DNDEBUG なし、assert 有効、ACL なし）
スコア1ケースの得点（最大650）を maximize・paired_difference で比較
時間ソルバー内部の予算は約1.95秒（問題文の付記に記載）
公式ツールRust 製。scripts/build_tools.sh でビルドして problem/tools/bin/（Git 管理外）に置く

8. 解法：現best の構成

現best（best/main.cpp、約2300行）は、発射の列を解の表現とし、ブロック巡回で作った多数の初期解を予選してから、4個体の集団で焼きなましつき大近傍探索（LNS）を回し、最後に厳密 DP とビームで仕上げる。全マスを塗り切る前提で、行動数 K を減らすことだけを狙う。

解の表現とコスト

解は Fire{x, d, L}（発射位置・方向・必要な長さ）の列である。発射の間は前計算した最短路で移動し、パワーが足りなければその場でパスして待つとみなす。こうすると、列から行動数とパワーの推移が一意に決まる（RouteTrace）。

dist   = D[pos][x]                 # BFS で前計算した最短距離
charge = max(dist, L − power)      # 移動数。足りない分はパスで補う
cost  += charge + 1                # +1 は発射
power  = (power + charge) / 2 + 1  # 発射後のパワー
# 実際に塗る長さは min(power + charge, 壁までの距離)。余分に塗っても害はない

この表現では「どこを・どの順で・どちら向きに撃つか」だけを探索すればよい。移動経路やパスの挿入は出力時に機械的に決まる。

時間配分

焼きなまし以降の区切りと局所の時間枠は、もともと1.75秒用だった。R0010 でこれらを 39/35 倍し、終了を1.95秒にした。前半の125msと245msは固定値である。

骨格の生成：ブロック巡回

  • 盤面を 4×4＝16 ブロック（基本は 5×5）に分け、各ブロックを「1辺に沿って歩きながら内側へ撃つ」パスで塗る。パスは「どの辺に沿うか（4通り）× 歩く向き（2通り）」の8通りと、それぞれの塗り残しを1発で補った版で、ブロックごとに最大16通りある。
  • 巡回順は、深さごとに (訪問済みブロック集合, 最後のパス) をラベルにした幅224のビームで決め、1回の呼び出しで最大5本の巡回を返す。評価は1/8行動単位で、塗り残しにペナルティを付ける。
  • 呼び出しごとに分割を変えて多様性を出す。均等な5×5、一部の切れ目を±1ずらした分割、転置、縦の切れ目を壁の隣へ寄せた分割（adjustCuts）を周期的に使う。
  • 巡回で塗り残したマスは repair で埋める。同じ発射列は重複として捨てる。

部品

部品役割
repair塗り残したマスに発射を挿入して埋める。塗りにくいマスから先に割り当てる。塗りにくさは「そのマスを含む長さ5以下の線分の候補数」で、少ないほど難しい（壁や角の近く）。利得は行・列の未塗りビットマスクと popcount で数える
tighten各発射の長さを、その発射だけが塗っているマスまでに縮める。不要になった発射は消す
optimizeShots撃ち方DP。発射の順序を固定し、各発射が担当するマスを覆う別の撃ち方（線分の反対端から逆向きに撃つ、塗り済みのマスまで伸ばして撃つ位置をずらす）を、(発射の番号, パワー) を状態とする DP で厳密に選ぶ
beamNeighborhood連続する数発を取り除き、それで塗られなくなったマス（64以下）をビームで置き直す。窓の外の発射を伸ばして先に覆えないかも試す（borrowCoverage）
chooseWindow窓の選び方。区間のコスト増・パワーの減り・塗ったマス数から損失を見積もり、壁際を少し優先して12回の抽選で最悪の区間を選ぶ
extendFreeShotsパワーに余裕がある発射を、行動数を増やさずに塗れる範囲まで伸ばす

集団焼きなましの近傍

1ステップで次のどれかを重み付きで選ぶ。破壊系（0〜5）のあとは repair と tighten で必ず全マスを塗れる状態に戻す。

重み近傍
7＋5矩形の窓（一辺6以下、塗りにくいマスが多い場所ほど選ばれやすい）に触れる発射を取り除く。触れる判定は線分全体か始点だけ
3連続する1〜8発を取り除く
3ランダムな1〜4発を取り除く
5＋31発、または隣り合う2発の位置・向き・長さを少し変える
2隣り合う2発の順序を入れ替える
13〜12発の区間の順序を反転する（半分の確率で各発射を線分の反対端から逆向きに撃つ形に変える）
11〜4発の区間を別の位置へ移す
51〜5発の窓に撃ち方DPをかける
120回に1回3〜9発の窓をビームで置き直す
  • 受理：Δ = Δ行動数 + 0.04 × Δ発射数。best を更新するか Δ≤0 なら受理し、それ以外は確率 exp(−Δ/temp) で受理する。温度は 1.16 から 0.17 へ指数的に下げる。
  • 途中の磨き：best を更新しそうな解（と64回に1回の近い解）には、3msの撃ち方DPをかけてから判定する。
  • 個体の回し方：先頭の個体に約29ms、他の3体に約11msずつ割り当てる。一巡ごとに順位を付け直し、上位の個体から下位の個体へ領域を移植する交叉をかける（下位の個体の、その窓に触れる発射を差し替えて修復する）。先頭の個体も、他の個体の領域を貪欲な受理で取り込めるか試す。4巡ごとに、best より3以上悪い個体を best の複製で置き換える。

評価の物差し

オーケストレーターが問題文から導いた上界がある。1発で塗れるマスはパワーと移動で決まり、「1マス移動して P=4 で新しい5マスを撃つ」の繰り返し（1行動あたり2.5マス）が最も効率がよい。ここから1ケースの得点は約 490 + 0.4M（M は壁の数）で抑えられ、M の平均15では約496になる。損失は、壁や盤端で線分が切れること、開始直後（P=0）、終盤、巡回の切り替えで生じる。

9. 解法の系譜（R0001〜R0011）

効果は、そのラウンドの seed で、直前の best と比べた平均の差である（正ほど良い）。ラウンドごとに seed が違うので、効果どうしを足し合わせても厳密な累計にはならない。

10. 知見と未解決の点

解法について

  • 時間を増やしても伸びにくい。R0007 時点の best に時間だけを与えると、4秒で +0.9、20秒で +2.1、100秒で +3.0（seed 0〜9）だった。伸びの大半は焼きなましの前、つまり試せる初期解の数が増えたことから来ていた。焼きなましは予算によらず約6〜7手しか減らさない。
  • この結果から、R0011 では「骨格を安く多数予選する」案を出し、採用された。次も、骨格の生成と選別、または停滞を抜ける構造的な近傍が狙い目になる。
  • 壁の少ない盤面（K が163〜166）は、初期解からほとんど改善しない。上界（M=0 で K≥160）との差は小さく、伸びしろは壁の多い盤面に偏る。

ハーネスについて

  • 利用上限や時間切れで止まった worker も、main.cpp があれば submitted として凍結される。区別は job.json の agent_outcome だけで、再実行の手段が無い（R0002・R0008・R0009 で発生）。
  • 使った engine は state.json にしか残らず、close で上書きされて消える。1ラウンドの中で claude と codex を混ぜることもできない。
  • workspace はリポジトリの中（runs/）にある。codex のサンドボックスは読み取りを制限しないので、外を読まない指示を破れば履歴に届く。
  • claude worker はテキスト出力なので、トークン使用量が記録されない。--output-format stream-json にすれば記録と利用上限の使用率が取れる。
