1. 要点

  • 記録は想定どおり取れた。R0012 の worker は10体すべて、呼び出しごとのトークンと使用率が残った。オーケストレーターの呼び出しは、ラウンドの作業だけが R0012 に入った（3章）。
  • ラウンドごとに新しいセッションにした効果は大きい。オーケストレーターが1回に読む文脈は、R0011 の54万から R0012 の9.5万へ、約1/5.6になった。リポジトリを読み直すので呼び出しは9回から40回に増えたが、キャッシュ読み出しは23%減った。
  • Codex の A（10体）1ラウンドで、5時間枠の45%、週間枠の7ポイントを使った。同じ5時間枠で A を回せるのは2回まで。
  • そのうち約22%は、実行中のコマンドを待つだけの呼び出しだった。worker が待ち時間を1秒以下に指定し、10秒ほどかかる quickcheck のたびに、結果を取りに行く呼び出しを足していた。task.md に1行書けば無くせる見込みで、成果物の質には影響しない（5章）。
  • worker の effort を high から medium に下げると、思考が関わる約25%の一部が減る。思考が半分になれば約13%。ただし質への影響は測れていないので、待ち時間の修正を先にする（6章）。
  • Claude と Codex は別々の利用枠。両者のトークン数を足したり比べたりはしない。オーケストレーター（Claude）の使用率は、対話セッションの記録に残らないため、まだ測れていない。

2. 指標と区分

サブスクで実際に制約になるのは、5時間枠と週間枠の使用率。そこで、主指標はラウンドごとの使用率の増分とする。トークン数は、その中身を見るために区分別に数える。

区分意味重みの目安Codex の推定（R0012、4章）
キャッシュなし入力キャッシュに無い入力。Claude Code ではほぼ0になる基準1
キャッシュ書き込み文脈の新しい部分を、キャッシュに載せた分入力より重いCodex は記録しない

件数ではキャッシュ読み出しが大半を占めるが、重みは小さい。R0012 の Codex の worker では、トークン数の94%がキャッシュ読み出しだったが、使用率への寄与は約48%だった。全部を足した1つの数字で判断すると誤るので、区分を分けて見る。

対話セッションの呼び出しは、ラウンドの作業のときだけ、そのラウンドに数えた。条件は次の2つ。

  1. そのラウンドの thin.cli コマンド（prepare〜close）を実行したセッションであること。
  2. 「prepare を実行したターンの開始」から「close を実行したターンの終わり」までの呼び出しであること。ただし、それより前のラウンドを実行していないセッション（そのラウンドのために始めたセッション）では、最初のターンから数える。前のラウンドの close より前には遡らない。

それ以外の呼び出し（ラウンドの合間の質問や相談、ドキュメントの整備、別のセッションでの作業）は「ラウンド外」として、セッションとターンごとに分けて数えた（11章）。

5. 考察：渡す情報とプロンプトで減らせるか

結論：減らせる。いちばん効くのは、渡す情報の量より、呼び出しの回数を減らす指示。worker の消費の約2割は、1行の指示で無くせる見込み。
手段減る見込み（Codex の5時間枠の消費に対して）質への影響変える場所
長いコマンドを1回で待たせる約22%（待つだけの呼び出し）なしtask.md の文面
quickcheck が実行時間と残り時間も出す約3%（時刻の確認）と、結果ファイルを開く手間なしquickcheck.py と run-workers
コードを小さくする読む量しだい（読んだコードと問題文は約23%）解法側の判断解法の作業として
task.md を短くするほぼ無い（task.md は入力の約1.5%）案が伝わりにくくなる-
Codex の固定分を減らす固定分は約14%。呼び出しが減れば一緒に減る-設定では難しい
  1. 長いコマンドを1回で待たせる。Codex の worker は、コマンドの待ち時間（exec_command の yield_time_ms）を毎回 1000ms か 100ms に指定していた。既定は10秒、上限は30秒。quickcheck はコンパイル（約6秒）と実行（約2秒）で10秒前後かかるので、ほぼ毎回途中で戻り、結果を取りに行く呼び出しが要った。61回のうち49回は quickcheck、残りもコンパイルなどの終了待ちだった。task.md に、たとえば「python3 quickcheck.py やコンパイルは10秒ほどかかる。yield_time_ms を 30000 にして、1回で終わりまで待つ」と書けば、ほぼ無くせる見込み。claude の worker は Bash が終了まで待つので、この問題は起きない。
  2. quickcheck が実行時間と残り時間も出す。worker は、20分の上限に対する残り時間を知るためだけに、時刻を8回確かめていた。quickcheck は得点しか出さないので、実行時間を見るために結果ファイルや stderr を開く呼び出しもあった。quickcheck の出力に、実行時間と worker の残り時間を入れれば、どちらも減らせる。
  3. コードを読む量は、渡し方では減らしにくい。親コードは2,500〜2,900行（約10万字）。worker は差分や範囲を指定して読み、全体は読んでいない。それでも、読んだ内容は後の呼び出しで毎回読み直されるので、約23%になる。減らすならコードそのものを小さくする手がある。たとえば現 best には、呼ばれていない関数（repairOld、218行）が残っている。ただし効果は worker の読み方しだいで、これは解法の作業として判断する。
  4. task.md を短くしても、ほとんど効かない。task.md は約850トークンで、全呼び出しで読み直しても入力の約1.5%。案の説明を削るほどの効果はない。
  5. オーケストレーターの側は、すでに小さい。R0012 でツールから受け取った結果は約8.7万字で、1回あたりの文脈は約10万。ここで大きいのは、渡す情報より、セッションの使い方（ラウンドごとに新しくする、長い待ちのあとに続けない）と effort。

6. 考察：worker の effort を high から medium に下げる意味

結論：消費は1割強減りうるが、質への影響が分からない。先に待ち時間を直し（約2割、質に影響なし）、それでも利用枠が足りなければ比べる。
  • 思考が関わるのは、5時間枠の消費の約25%。内訳は、思考の出力が約17%、その思考を後の呼び出しで読み直す分が約9%。Codex は、思考も次の呼び出しの入力に入れている（入力の増え方が、262区間のすべてで直前の出力全体以上だった）。
  • medium で思考が半分になれば、約13%減る計算。ただ、思考がどれだけ減るか、試行錯誤が増えて呼び出しが増えないかは、このデータからは分からない。呼び出しが1割増えれば、節約の大半が消える。
  • 時間の上限は効いていない。R0012 の worker は全員20分以内（最長17.4分）に終わった。effort を下げる理由になるのは利用枠だけ。
  • 質への影響が大きくなりうる課題。この課題は、2,500〜2,900行のコードの間で変更を移し、時間の配分を調整する作業。R0012 の効果は −0.084〜+0.109 と小さく、10案の上位から採用が決まる。worker の質が少し下がるだけで、採用できる改善が減りうる。
  • 確かめ方。トークンの差は1ラウンドで測れるが、質の差は10体では見分けにくい。同じ10案を medium で再実行し、案ごとに high と比べるのが最も比べやすい。それでも1回では判断しにくいので、利用枠が実際に足りなくなってから検討すればよい。
  • オーケストレーター（Claude、xhigh）は別の枠。R0012 では出力3.9万のうち思考が2.3万（60%）。使用率が測れていないので、判断の材料はまだ無い。

7. 次の節約候補

効果は、次のラウンドからの記録で確かめる。見る数値も書いておく。

  1. 済み オーケストレーターをラウンドごとに新しいセッションで始める。R0012 で、1回あたりの文脈が54万から9.5万に下がった。
  2. 長いコマンドを1回で待たせる（Codex の worker）。見込みは5時間枠の消費の約22%。見る数値：待つだけの呼び出しの回数、A の1ラウンドの5時間枠の増分（R0012 は45ポイント）。
  3. quickcheck が実行時間と残り時間も出す。見る数値：時刻を確かめる呼び出しの回数。
  4. 長い待ちのあとは、新しいセッションで続ける。1時間を超えて待つと、どのみち文脈全体を書き直すことになる（R0012 の close のあとも約8万を書き直した）。見る数値：キャッシュ書き込み。
  5. worker の effort を見直す。2と3のあとで、利用枠が足りないときに検討する（6章）。見る数値：思考の出力、呼び出し回数、採用率。
  6. オーケストレーターの effort を見直す。出力の約6割が思考。Claude の使用率を測れるようにしてから判断する。
  7. claude の worker の固定分を減らす。--safe-mode でも、道具の定義などで1回あたり約3万を読む（Haiku の試行）。道具を絞るフラグ（--tools）で減らせるか確かめる。見る数値：worker の最初の呼び出しの文脈。
  8. A の並列数と時間の上限を、記録から決め直す。R0012 では20分の上限に達した worker はいなかった。10体で5時間枠の45%を使うので、1つの5時間枠で回せる A は2回まで。

13. 集計の限界

  • Claude Code の記録は、1つの応答を content block ごとに別の行に書き、同じ usage を繰り返す。message.id で重複を除いた。ある1セッションでは、重複を除いた合計が Claude Code 自身の集計（cost-state）より約7%少なかった。原因は分かっていないので、数値は概数として扱う。
  • Codex の input_tokens はキャッシュ分を含む。キャッシュ分を引いて、Claude と同じ区分に揃えた。
  • Codex の重み（4章）は、R0012 の1ラウンドから推定した目安。使用率は1ポイント刻みで、3つの区分は一緒に増えるので、比は大まかにしか決まらない。提供元が公表している値ではない。
  • 出どころ別の内訳（4章）は、入力の増え方を、その間に受け取ったツールの出力の文字数で按分した推定。
  • codex の worker の旧形式（turn.completed）は合計しか無く、呼び出し回数と文脈の大きさは分からない。
  • ラウンドへの割り当て（2章）は、コマンドとターンからの推定。prepare より前の別のターンで案を考えた分は、ラウンド外になる。逆に、ラウンドの途中のターンでした別の作業は、ラウンドに入る。
  • そのラウンドのために始めたセッションでは、最初のターンから数えるので、セッションを始めたときの理解や確認も入る（R0001、R0006、R0012）。
  • ~/.claude の記録は、既定の設定では30日で消える。close のときに runs/R####/usage.json へ写している。

14. 記録の仕組み

  1. claude の worker：--output-format stream-json --verbose を付けた。agent.stdout は、呼び出しごとの usage と利用上限の使用率を含む JSONL になる。最終メッセージは agent.last_message.md に書き出す。
  2. codex の worker：--ephemeral を外し、念のため --disable memories を付けた。worker が終わると、run-workers がその worker のセッション記録を ~/.codex/sessions から jobs/<id>/codex_rollout.jsonl へ移す。止められた worker も、そこまでの呼び出しごとのトークンと使用率が残る。
  3. job.json：engine・モデル・effort と、トークンの要約（usage：呼び出し回数、各区分、最大の文脈、使用率の始めと終わり）を書く。
  4. close：ラウンドの消費（対話セッション、worker、使用率）を runs/R####/usage.json に書く。
  5. 対話セッションの割り当て：時刻だけで割り当てると、ラウンド中の別の作業（このレポートの作業など）や、ラウンドの合間の作業が混ざる。そこで、コマンドを実行したセッションとターンで割り当てる（2章）。usage.json は close のときに書き、close のあとの報告を含めるため、次のラウンドの close のときに確定する。
  6. 使用率の期間：Codex の resets_at は、同じ期間でも読み取りごとに1秒ずれる。2分以内のずれは同じ期間として扱う（R0012 のあとで直した）。
  7. 集計：python3 scripts/token_report.py（表）、--outside（ラウンド外をターンごと）、--jobs R0012（worker ごと）、--json、--save（確定していない usage.json の書き直し）。
codex の痕跡について：--ephemeral を外すと、記録ファイルを移しても、Codex 自身の SQLite（~/.codex/state_5.sqlite のスレッド一覧と thread_history_1.sqlite）に、スレッドのタイトル（task.md の冒頭約80字）と中身が残る。--ephemeral のときは何も残らなかった。worker のサンドボックスは読み取りを制限しないので、後の worker は読もうと思えば読める。ただし runs/ も同じく読めるので、漏れうる中身の範囲は変わらない。監査（codex_audit.py）は、workspace の外のパスへの参照を注意として出す。
集計スクリプト：scripts/token_report.py（集計の中身は thin/usage.py）。数値は 2026-11-19 時点のログによる。4章の推定は、R0012 の worker の記録（runs/R0012/jobs/*/codex_rollout.jsonl）から計算した。
