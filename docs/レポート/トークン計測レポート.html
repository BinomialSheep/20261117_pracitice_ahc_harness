1. 要点

  • いちばん大きいのは、オーケストレーターの文脈の積み上がり。準備から R0011 までを1つのセッションで進めたため、1回の呼び出しで読む文脈が R0001 の17万から R0011 の54万へ、ほぼ単調に増えた。同じ作業でも、1回あたりの読み出しは約3.2倍になっている。
  • 長く待つと、キャッシュの書き直しが起きる。キャッシュの有効期限は1時間。worker の実行や評価で2時間51分・8時間15分待ったあとの呼び出しで、文脈全体（26万・37万）を書き直していた。このセッションのキャッシュ書き込み全体（110万）の57%がこの2回。
  • worker の記録は大半が欠けていた。claude の worker は最終メッセージしか残しておらず、codex の worker は20分の上限で止められると何も残らなかった。今回のハーネス変更で、どちらも呼び出しごとに残るようにした（9章）。
  • 完走した codex worker は、1体あたりキャッシュ読み出し約117万・出力約1.6万。A の1ラウンド（10体）で、キャッシュ読み出しは1,000万を超える（R0011 で1,278万）。
  • Claude と Codex は別々の利用枠で、トークンの重みも違う。両者のトークン数を足したり比べたりはしない。

2. 指標と区分

サブスクで実際に制約になるのは、5時間枠と週間枠の使用率。そこで、主指標はラウンドごとの使用率の増分とする。ただしこれまでのログにはほとんど残っていないので（7章）、この報告ではトークン数を区分別に見る。

区分意味重みの目安
キャッシュなし入力キャッシュに無い入力。Claude Code ではほぼ0になる基準
キャッシュ書き込み文脈の新しい部分を、キャッシュに載せた分入力より重い
キャッシュ読み出し前の呼び出しと同じ部分を、もう一度読んだ分。毎回、文脈全体を読み直す入力の約1/10
出力モデルが書いた分。思考を含む入力の数倍

件数ではキャッシュ読み出しが大半を占めるが、重みは小さい。全部を足した1つの数字で判断すると誤るので、区分を分けて見る。

対話セッションの呼び出しは、ラウンドの作業のときだけ、そのラウンドに数えた。条件は次の2つ。

  1. そのラウンドの thin.cli コマンド（prepare〜close）を実行したセッションであること。
  2. 「prepare を実行したターンの開始」から「close を実行したターンの終わり」までの呼び出しであること。ただし、それより前のラウンドを実行していないセッション（そのラウンドのために始めたセッション）では、最初のターンから数える。前のラウンドの close より前には遡らない。

それ以外の呼び出し（ラウンドの合間の質問や相談、ドキュメントの整備、別のセッションでの作業）は「ラウンド外」として、セッションとターンごとに分けて数えた（6章）。

8. 集計の限界

  • Claude Code の記録は、1つの応答を content block ごとに別の行に書き、同じ usage を繰り返す。message.id で重複を除いた。ある1セッションでは、重複を除いた合計が Claude Code 自身の集計（cost-state）より約7%少なかった。原因は分かっていないので、数値は概数として扱う。
  • Codex の input_tokens はキャッシュ分を含む。キャッシュ分を引いて、Claude と同じ区分に揃えた。
  • codex の worker の旧形式（turn.completed）は合計しか無く、呼び出し回数と文脈の大きさは分からない。
  • ラウンドへの割り当て（2章）は、コマンドとターンからの推定。prepare より前の別のターンで案を考えた分は、ラウンド外になる。逆に、ラウンドの途中のターンでした別の作業は、ラウンドに入る。
  • そのラウンドのために始めたセッションでは、最初のターンから数えるので、セッションを始めたときの理解や確認も入る（R0001、R0006）。
  • ~/.claude の記録は、既定の設定では30日で消える。今後は close のときに runs/R####/usage.json へ写し、R0001〜R0011 の分も書き出した。

9. 今回入れた記録の仕組み

  1. claude の worker：--output-format stream-json --verbose を付けた。agent.stdout は、呼び出しごとの usage と利用上限の使用率を含む JSONL になる。最終メッセージは agent.last_message.md に書き出す。
  2. codex の worker：--ephemeral を外し、念のため --disable memories を付けた。worker が終わると、run-workers がその worker のセッション記録を ~/.codex/sessions から jobs/<id>/codex_rollout.jsonl へ移す。止められた worker も、そこまでの呼び出しごとのトークンと使用率が残る。
  3. job.json：engine・モデル・effort と、トークンの要約（usage：呼び出し回数、各区分、最大の文脈、使用率の始めと終わり）を書く。
  4. close：ラウンドの消費（対話セッション、worker、使用率）を runs/R####/usage.json に書く。
  5. 対話セッションの割り当て：時刻だけで割り当てると、ラウンド中の別の作業（このレポートの作業など）や、ラウンドの合間の作業が混ざる。そこで、コマンドを実行したセッションとターンで割り当てる（2章）。usage.json は close のときに書き、close のあとの報告を含めるため、次のラウンドの close のときに確定する。
  6. 集計：python3 scripts/token_report.py（表）、--outside（ラウンド外をターンごと）、--jobs R0012（worker ごと）、--json、--save（過去分の書き出し）。
codex の痕跡について：--ephemeral を外すと、記録ファイルを移しても、Codex 自身の SQLite（~/.codex/state_5.sqlite のスレッド一覧と thread_history_1.sqlite）に、スレッドのタイトル（task.md の冒頭約80字）と中身が残る。--ephemeral のときは何も残らなかった。worker のサンドボックスは読み取りを制限しないので、後の worker は読もうと思えば読める。ただし runs/ も同じく読めるので、漏れうる中身の範囲は変わらない。監査（codex_audit.py）は、workspace の外のパスへの参照を注意として出す。

どちらの engine も、Haiku と effort low の短い試行で、run-workers と同じ処理を通して確かめた。

10. 次の節約候補

効果は、次のラウンドからの記録で確かめる。見る数値も書いておく。

  1. オーケストレーターをラウンドごとに新しいセッションで始める。状態はファイルにあり、AGENTS.md の手順1で再開できる。1回あたりの文脈が約50万から数万に下がる見込み。見る数値：平均の文脈、キャッシュ読み出し、使用率の増分。
  2. 長い待ちのあとは、新しいセッションで続ける。1時間を超えて待つと、どのみち文脈全体を書き直すことになる。1と合わせると効果が大きい。見る数値：キャッシュ書き込み。
  3. オーケストレーターの effort を見直す。出力の約6割が思考。案の作成と採否の判断に必要な水準を、結果を見ながら決める。見る数値：出力・思考と、採用率。
  4. claude の worker の固定分を減らす。--safe-mode でも、道具の定義などで1回あたり約3万を読む（Haiku の試行）。道具を絞るフラグ（--tools）で減らせるか確かめる。見る数値：worker の最初の呼び出しの文脈。
  5. A の並列数と時間の上限を、記録から決め直す。止められた worker の消費が分かるようになったので、20分の上限に達した worker が成果に見合っているかを確かめる。
